# 保育士試験一問一答アプリ 実装計画

## 1. 実装計画の目的

この文書は、`docs/SPEC.md` の確定仕様を、React初学者がJavaScriptとJSXで一つずつ実装・確認できる小さな作業に分けた計画である。TypeScriptは使用しない。

一度の依頼ではチェック項目を1つだけ実装し、動作確認とコード確認が終わってから次へ進む。各Stepの途中でも、可能な限り画面が起動する状態を保つ。

この文書は実装順と実装方法を提案するものであり、仕様自体は変更しない。見積時間は扱わない。

確認した現行仕様は次のとおりである。

- App Routerの `page.js` または `page.jsx` は既定ではServer Componentである。
- `useState`、イベント処理などの対話機能にはClient Componentが必要である。

- Server ComponentからClient Componentへ渡すpropsは、シリアライズ可能な値にする必要がある。
- Server Componentでは、決定的な処理としてローカルファイルの同期読み取りを行える。
- `app/layout.js` または `app/layout.jsx` から読み込まれたグローバルCSSはアプリ全体に適用される。

## 4. 実装の基本方針

- `docs/SPEC.md` の確定仕様だけを実装する。
- アプリコードはJavaScriptとJSXで記述し、TypeScriptの型注釈や型定義ファイルは使用しない。
- JavaScriptだけのファイルは `.js`、JSXを含むファイルは `.jsx` とする。
- 各Stepは単独で依頼し、完了後に停止する。
- 基本の画面を確認してから、次の画面や操作を1つずつ追加する。
- URLは分けず、トップページ `/` の中で表示を切り替える。
- stateは対話処理をまとめる親コンポーネントで `useState` により管理する。
- 同じ内容を複数のstateへ重複して保存せず、選択位置から求められる科目・テーマ・問題はその都度データから取得する。
- `useEffect` は使用しない計画とする。画面移動時の初期化は、クリック時に呼ぶ意味の分かる関数内で行えるためである。
- Context API、カスタムフック、状態管理ライブラリは使用しない。
- 最初から細かい共通部品を作らない。役割が確定してファイルが読みにくくなった段階で、画面単位に分ける。
- `assets/question_data.js`、`参考資料.html` は変更しない。
- 問題数は `quantity` ではなく `questions.length` を使う。
- 動作確認には各Stepで `npm run lint` を使い、画面変更時はブラウザでも確認する。区切りの大きい段階と最終段階では `npm run build` も確認する。TypeScriptの型チェックは確認項目に含めない。
- 厳格なTDDやテストライブラリ追加は行わない。

## 5. 推奨する画面管理とstate管理の方針

### 5.1 画面の切り替え

5画面でURLを分けず、`currentScreen` という1つのstateで表示を切り替える方法を推奨する。

`currentScreen` が持つ値は、次の5種類とする。

- `"subjects"`: 科目選択画面
- `"themes"`: テーマ選択画面
- `"intro"`: テーマ紹介画面
- `"question"`: 一問一答画面
- `"result"`: 結果画面

理由は、初回版ではURL履歴の仕様がなく、同じページ内の短い学習手順だからである。ルーティングを増やさず、クリックによってstateが変わり、再描画されるReactの基本を追いやすい。

### 5.2 stateの置き場所

対話部分の親となる `QuizApp` に、次の最小限のstateを置く。

| state | 役割 |
| --- | --- |
| `currentScreen` | 現在表示する画面 |
| `selectedSubjectIndex` | 選択した科目の配列位置。未選択は `null` |
| `selectedThemeIndex` | 選択したテーマの配列位置。未選択は `null` |
| `currentQuestionIndex` | 現在の問題の配列位置 |
| `selectedChoiceIndex` | 選んだ選択肢の元データ上の位置。回答前は `null` |
| `currentCorrectCount` | 今回の一問一答で正解した数 |
| `usersData` | 現在のブラウザ表示中の問題別回答状況 |
| `displayChoices` | 並び替え後の選択肢と元位置。第8段階で追加 |

選択中の科目、テーマ、問題そのものはstateへ重複保存しない。各indexと `subjects` から求める。

回答済みかどうかは `selectedChoiceIndex !== null` から分かるため、別の `isAnswered` stateは作らない。

### 5.3 `users_data` と再描画

サーバーから受け取った初期データを `useState` の初期値として `usersData` に保持する。回答時は元のオブジェクトを直接書き換えず、対象問題の `solved` だけを変えた新しいオブジェクトをstateへ設定する。

Reactはstateが新しい値になったときに再描画するため、テーマ画面の正解数と進捗も更新される。入れ子のデータを安全に更新するため単純なスプレッド構文が必要になるが、使用するStepで仕組みを説明する。

永続保存は行わない。再読み込みするとサーバーから初期値が再び渡される。

### 5.4 選択肢の並び替え

並び替え対象の各選択肢を、次の2つを持つ単純なオブジェクトとして扱う。

- `text`: 表示する選択肢文
- `originalIndex`: 元の `choices` 配列での位置

表示順だけを変え、正誤判定は `originalIndex` と `answer` を比較する。並び順が回答後の再描画で変わらないよう、作成した並びを `displayChoices` stateへ保存する。

## 6. 推奨するコンポーネント構成

### 6.1 最終的な推奨構成

```text
app/
├─ components/
│  ├─ SubjectSelectionScreen.jsx
│  ├─ ThemeSelectionScreen.jsx
│  ├─ ThemeIntroScreen.jsx
│  ├─ QuestionScreen.jsx
│  └─ ResultScreen.jsx
├─ QuizApp.jsx
├─ globals.css
├─ layout.jsx
└─ page.jsx
lib/
└─ loadQuestionData.js
```

### 6.2 各ファイルの役割

- `app/page.jsx`: Server Componentのまま、問題データを読み、`QuizApp` に渡す。
- `lib/loadQuestionData.js`: サーバー上で `assets/question_data.js` を読み、`subjects` と `users_data` のJSON部分を取り出す。`eval` は使わない。
- `app/QuizApp.jsx`: `'use client'` を付け、画面とstate、画面移動の関数をまとめる。
- `app/components/*Screen.jsx`: 各画面の表示を担当し、必要な少数の値とクリック関数をpropsで受け取る。
- `app/globals.css`: 読みやすさと操作しやすさに必要な最低限のスタイルを持つ。

### 6.3 分割する時期

第1〜第8段階では、処理の流れを追いやすいよう、主に `QuizApp.jsx` 内で画面を作る。全機能が動いた後、第9段階で画面単位に分ける。

最初からボタンやカードの共通コンポーネントは作らない。同じ表示が実際に重複し、共通化の必要性が明確になった場合だけ、その後に検討する。カスタムフックとContext APIは使わない。

## 12. 実装前または実装中に確認が必要な点

### 実装前に計画として確認する点

`assets/question_data.js` は変更禁止である一方、ES Moduleの `export` を持たない。この計画では、次の方法を推奨案として確定している。

1. Server Component側だけでNode.js標準機能を使ってファイルを読む。
2. `subjects` と `users_data` の値はJSONとして解釈できる範囲を切り出し、`JSON.parse` する。
3. 読み取ったオブジェクトをClient Componentへpropsで渡す。
4. 元データの編集、データの複製、`eval`、追加ライブラリを避ける。

この方針を変更したい場合だけ、Step 1の実装前に人間の確認が必要である。方針を承認する場合、初回版の仕様に関する未解決事項はない。

### 実装中に停止して確認する条件

- `question_data.js` の形式が変わり、安全にJSON部分を切り出せなくなった場合
- 確定仕様を満たすために `assets/question_data.js` の変更が必要になった場合
- Next.jsのローカルドキュメントと実際の挙動が一致しない場合
- 追加ライブラリや設定変更が必要になった場合
- SPEC.mdにない表示や動作を追加する必要が生じた場合

これらが起きた場合は回避策を勝手に入れず、原因と選択肢を説明して人間の判断を待つ。
